# 第二轮主动纠察：玩法逻辑、数据安全与经济系统

审查日期：2026-11-11
范围：服务端角色/物品 RPC、背包、装备、掉落、交易、魔物数据与数值系统。
方法：静态源码审查。未运行服务端、未做渗透测试或真实多客户端测试。以下“确定问题”均由代码路径直接支持；运行时影响仍需复现确认。

## 本轮新发现（不是重复汉化问题）

### P0-1 装备 RPC 存在“无库存装备”路径
涉及：
- `sources/network/server/Server.gd` 的 `EquipItem()`：客户端传入 itemID/customfield/itemIndex 后，只检查物品定义存在、slot 有效、玩家存活和背包对象存在。
- `sources/actor/Inventory.gd` 的 `EquipItem()`：当 itemIndex 无效或不匹配时，直接 `Item.new(cell)` 创建一个新 Item 并装备，而不是拒绝请求。

风险：恶意或异常客户端可能提交任意已定义装备的 ID 和无效索引，服务端仍创建装备实例、应用属性修正并保存装备。可能导致凭空装备/属性作弊。
修复要求：服务端必须验证玩家背包中确实持有该物品、索引/ID/customfield完全匹配、该物品未被其他槽位占用；无效索引直接拒绝。只有经过服务器确认的背包 Item 实例可以进入装备槽。添加伪造 RPC 请求测试。

### P0-2 使用物品 RPC 丢失 customfield
涉及：
- 客户端 `ItemCell.Use()` 可以识别 id 和 customfield。
- `Server.UseItem(itemID, peerID)` 只接收 itemID。
- 服务端 `DB.GetItem(itemID)` 未传 customfield。
- 背包 `UseItem(cell)` 再按 cell 身份找物品。

风险：同一个基础 ID 存在不同 customfield 变体时，可能取错物品定义、使用失败或错误消费。此类变体也可能承载随机词条/品质/耐久等数据。
修复要求：RPC 参数必须包含 customfield 或明确的实例唯一 ID；服务端按背包真实实例解析，客户端不得决定效果。

### P1-3 HasItem 对可堆叠物品只检查第一个堆叠
涉及：`Inventory.gd` 的 `HasItem()`。
当前可堆叠物品遇到第一个匹配条目就立即返回 `item.count >= count`，不会累计后续相同物品堆叠；但 `GetItemCount()` 会遍历累计。
风险：若导入数据、旧存档或交易流程中出现同物品多个堆叠，材料检查会错误显示不足，导致制作/任务/交易判断不一致。
修复要求：可堆叠物品按所有匹配条目求和；或在导入时强制合并并加入一致性断言。补充多堆叠回归测试。

### P1-4 背包容量检查与实际堆叠规则可能不一致
涉及：`Inventory.HasSpace(count)` 把传入 count 直接当作槽位数量；而 `PushItem()` 对可堆叠物品会尝试合并到已有堆叠。
风险：在交易或批量发放时可能误判空间，出现明明可合并却拒绝、或对非堆叠物品与堆叠物品采用不一致容量语义。
修复要求：容量校验接收具体 addCounts，按每种物品 stackable 与当前堆叠状态模拟最终槽位数；不能只传一个模糊 count。为满包、已有堆叠、多个新物品组合做测试。

### P1-5 交易结算不是显式数据库事务
涉及：`WorldTrade.Commit()`。
当前先对双方做内存校验，Detach 后分别 ApplyExchange，再分别 SpendGP/AddGP，最后调用 RefreshCharacter。代码未显示将双方物品与金币交换包在单个数据库事务中。
风险：进程中断、数据库写入失败或某一方更新异常时，可能出现一方扣除成功、另一方未收到，或内存与持久化数据不一致。
修复要求：交易使用单个 SQL transaction：重新锁定/校验双方资产 → 双方扣除和增加 → 更新金币与库存 → commit；任何一步失败 rollback。锁定状态应绑定 revision，防止旧确认包结算新报价。

### P1-6 怪物掉落创建时缺少明确的容量/失败反馈策略
涉及：`BaseAgent.AddItem()` 调用 `inventory.PushItem(item, 1)`，没有检查返回值。
风险：如果怪物库存容量达到限制，掉落物加入怪物库存失败会被静默忽略，玩家可能永远拿不到配置掉落。
修复要求：怪物掉落不应依赖玩家背包容量逻辑；生成掉落时检查结果并记录日志/错误，保证关键掉落不会静默丢失。明确普通掉落、必掉任务物和装备掉落的失败处理。

### P1-7 经验表越界后的返回值语义不清
涉及：`Experience.GetNeededExperienceForNextLevel()`。
超过表长度返回 `MAX_LEVEL_REACHED = 0`，需要追踪所有调用者是否把 0 当成“已满级”或作为除数/阈值。
风险：等级上限边界可能出现错误升级提示、进度条异常或重复升级逻辑。
修复要求：查明所有调用点；明确最大等级常量；等级达到上限后禁止继续分配/升级，UI显示满级状态。补测最后一级及超界存档。

### P1-8 地图导航生成点使用 Vector2.ZERO 作为失败哨兵
涉及：`WorldNavigation.GetSpawnPosition()`。
位置(0,0)可能是有效地图坐标，但函数把 ZERO 当成“未找到位置”，会将合法位置替换成随机位置；同时随机导航点在没有三角网格时 assert。
风险：特定地图中心点刷怪位置被改写；地图导航数据缺失时服务端可能直接断言中断。
修复要求：使用显式 bool/可选结果表示是否找到位置，不以合法坐标充当失败值；地图加载时校验导航网格并优雅报错。

### P2-9 账号密码重置流程存在可用性与持久化风险待核查
涉及：`EmailService.gd` 的 pendingResets 存储为内存 Dictionary。
当前重置码在服务进程内存中保存；服务重启后会丢失。邮件发送失败时仍已创建重置记录，调用方也没有把 HTTP 发送失败状态同步给用户。
风险：用户可能收到“已发送”但实际未发送，或服务器重启后验证码失效。需进一步检查验证码尝试次数、请求频率和账户枚举防护。
修复要求：重置记录持久化、验证码尝试次数限流、邮件发送状态可追踪、错误提示避免泄露账户是否存在。

### P2-10 新手玩法目标与上游多人 MMO 结构存在范围冲突
源码已有账号、在线列表、玩家交易、网络同步、服务器/客户端架构；而当前目标首先是手机浏览器/安卓可玩的单人刷装体验。
风险：如果不先决定首发单人/离线或在线多人，掉落归属、装备实例、存档权威、职业平衡和部署成本会重复返工。
修复要求：MVP明确采用“单人优先、服务器权威数据可兼容扩展”的边界；暂不扩展玩家交易和复杂多人经济，先完成单人刷怪—拾取—装备—存档闭环。

## 本轮优先修复顺序

1. P0-1 装备请求必须验证真实库存持有。
2. P0-2 使用物品必须传递并验证 customfield/实例。
3. P1-3/4 统一堆叠、容量与背包规则。
4. P1-5 交易结算事务化（多人交易若暂不进入 MVP，可先关闭/隔离，不必抢占单人闭环资源）。
5. P1-6 确保掉落不静默丢失。
6. P1-7 等级上限边界。
7. P1-8 地图坐标与导航失败语义。
8. P2-9 密码重置可靠性与安全性。
9. P2-10 明确单人优先 MVP 架构边界。

## 本次禁止做出的结论

- 不能仅凭静态代码就宣称已复现漏洞或已修复。
- 不能声称交易可以被实际利用，除非构造客户端请求和故障注入复测。
- 不能将计划文档视为玩法已完成。
- 修复后必须跑 Godot headless 检查、服务器构建、Android 构建，以及对应回归测试。
