# 资深 Godot 游戏开发规范（项目内执行版）

版本：1.0
适用项目：Eternal World（Godot 4.7，像素风、手机优先、可浏览器/Android运行）
参考知识库：thedivergentai/Game-Dev-Agentic-Skills 的 godot-master，以及 Godot 官方 Best Practices。
参考入口：
- https://github.com/thedivergentai/Game-Dev-Agentic-Skills/tree/main/skills/godot-master
- https://docs.godotengine.org/en/stable/tutorials/best_practices/index.html
- https://github.com/thedivergentai/Game-Dev-Agentic-Skills/tree/main/skills/godot-save-load-systems

## 0. 使用边界

这份规范是项目的工程检查清单，不是要求把第三方 skill 的所有建议机械搬进项目。
每条建议先对照当前 Godot 4.7、Source of Mana 原架构、服务器/客户端模型和目标平台验证。禁止为了“架构先进”重写稳定的上游模块。
优先小补丁、可回滚、可测试；发现现有机制可复用时先复用。

## 1. 开发前：先弄清现状

每个需求开始前，必须：
1. 找到实际入口、调用链、数据所有者、持久化位置、相关 UI 和测试。
2. 阅读调用方与被调用方，不凭单个函数片段下结论。
3. 检查已有功能、插件和上游实现，避免重复造系统。
4. 明确影响范围、兼容风险、迁移方案、回滚方法。
5. 把需求拆成最小可验收补丁，先写验收标准再动代码。

## 2. 架构：状态只能有一个权威所有者

对每份状态回答：
- 谁拥有数据？
- 谁可以修改？
- 谁需要获知变化？

区分静态定义、运行时状态、界面表现和存档快照。
UI只展示数据并发出操作请求；不能自己改金币、装备、伤害、库存或任务状态。
服务端权威字段只能由服务端验证并写入。客户端只发意图，不直接决定结果。
优先使用现有架构与信号/事件边界，不新增无必要的全局单例。

## 3. RPG内容：数据驱动，不复制脚本

装备、怪物、技能、掉落、任务、配方尽量采用数据资源/配置定义。
新增一把武器优先新增数据，不复制一份武器逻辑脚本。
物品定义与物品实例分离：
- 定义：基础ID、名称、图标、基础属性、可装备部位、堆叠规则。
- 实例：品质、随机词条、强化等级、耐久、唯一实例ID。
随机词条必须进入权威实例数据并可持久化；不得只改 UI 文本或共享 Resource 原件。
每种材料必须有明确用途；每个技能必须有可观察效果；套装效果必须能触发并可测试。

## 4. 战斗、掉落与经济防坑

- 伤害、掉落、金币、装备属性和交易由权威端计算。
- 任何 RPC 都要验证玩家身份、距离/状态、物品归属、数量、冷却、目标合法性和请求频率。
- 装备必须来自真实库存实例；无效索引/ID/customfield直接拒绝，禁止服务端按客户端参数凭空 new 装备。
- 使用物品按实例ID或完整 customfield 精确解析，验证后再扣除和应用效果。
- 堆叠数量必须累计所有匹配堆叠；容量检查必须模拟真实合并规则。
- 掉落生成失败必须可见、可记录、可恢复，关键任务物品不能静默丢失。
- 交易必须原子结算；先锁定/复核双方资产，再一次性扣除、增加并提交，失败整体回滚。
- 概率掉落采用可复现测试种子；概率和经济产出要通过批量模拟检查极端值与通胀。

## 5. 存档与补丁：先保住玩家进度

- 存档包含 schema_version / save_version。
- 每次结构变化提供迁移逻辑；旧存档缺字段时有安全默认值。
- 先备份，再临时文件写入，校验成功后原子替换；保留可恢复备份。
- 不保存 Node/Scene 对象引用；只保存稳定ID和纯数据。
- 设置与角色进度分开管理。
- 资源补丁有 manifest、版本、SHA-256、文件大小、兼容版本和回滚指针。
- 下载先写临时目录，校验全部通过再切换活动版本；失败不覆盖当前可用版本。
- Android原生代码更新通常需要新APK；网页资源和数据可增量更新。不得承诺“所有内容都无需重新安装”。
- 数据库 schema migration 与资源补丁分开版本管理；补丁失败不能损坏数据库和存档。

## 6. UI、中文与手机体验

- 玩家可见文本集中管理，禁止新代码继续散落硬编码英文。
- 简体中文字体必须覆盖常用汉字、标点和数字；字体 fallback 需在导出包中验证。
- UI适配小屏、刘海安全区、虚拟键盘和不同宽高比。
- 触控按钮应有足够尺寸与间距，避免依赖 hover；所有核心流程纯触屏可完成。
- 文字不得截断、重叠、缺字或被弹窗遮挡。
- 浏览器音频必须有用户手势启动；断网、刷新和浏览器后台切换要有明确行为。
- 每个关键 UI 场景应可独立启动检查；交互状态必须有加载、成功、失败、禁用反馈。

## 7. 性能与资源管理

- 不凭感觉优化；先用 Godot Profiler / Monitors 建立基线。
- 不在每帧热路径动态加载资源、遍历全场景树、创建大量临时对象或打印日志。
- 大资源异步加载并显示加载反馈；重复刷怪/特效评估对象复用。
- 手机和浏览器以最低目标设备实测；关注帧时间尖峰、内存峰值、下载体积和耗电。
- 像素艺术资源统一尺寸、过滤、压缩和导入设置，防止模糊与重复导入。

## 8. 测试：代码通过不等于游戏可玩

每个补丁至少包含：
1. 静态检查/解析检查。
2. 对应逻辑单元或脚本测试。
3. 关键路径集成测试。
4. Android/Web导出构建（按受影响平台）。
5. 实机或真实浏览器操作验证。
6. 存档升级/回滚验证（若涉及数据）。
7. 旧功能回归检查。

核心玩家流程必须能完整走通：
启动 → 登录/本地进入 → 创建男女角色 → 进入村庄 → 对话/接任务 → 战斗 → 掉落 → 拾取 → 背包 → 穿戴/使用 → 属性变化 → 商店/制作 → 保存 → 退出 → 重进。

必须覆盖异常分支：背包满、金币不足、网络中断、服务器拒绝、重复点击、无效物品ID、伪造RPC、存档损坏、补丁中断、旧版本存档。

## 9. 交付报告格式

每次交付必须写清：
- 本次改动文件与功能。
- 哪些数据结构/接口变化。
- 是否影响旧存档、补丁、客户端/服务端兼容。
- 自动化检查结果。
- 构建结果及产物。
- 手机/浏览器实测结果。
- 未完成项、已知风险和回滚方式。

状态必须区分：
- 已提交（代码已入库）
- 已通过静态检查
- 已通过自动化测试
- 已成功构建
- 已在目标设备实测
- 已发布

任何未实际执行的检查标记“未验证”，不允许写“已完成”。

## 10. 本项目的优先级规则

P0：登录/创建角色/中文字体/存档安全/服务端物品校验/核心操作可用。
P1：刷怪掉落、装备实例、属性变化、技能与背包闭环。
P2：套装、词条流派、生活技能、收集和地图扩展。
不得因追求内容数量，绕过 P0/P1 稳定性。
